# Plan.md: Verde Marea Booking System — MVP

## 1. Текущий статус

- Приоритет: `P0`
- Текущее состояние: документы этапа 1 составлены, реализация не начата
- Основная цель цикла: рабочая система бронирования столов с локальным запуском, готовая к приёмке по всем 7 этапам курсового ТЗ
- Обязательное ограничение: локальный запуск, без внешних интеграций, без публичного деплоя, без лишнего production-контура
- Основной контекст проекта: `specification.md`, `design.md`
- Секреты: `DATABASE_URL` и любые токены — только в `.env` (не в `.env.example`, не в коммитах, не в ответах ИИ)
- Сейчас в работе: шаг 1 «Легенда, роли и план»

## 1.1 Целевой сценарий

Гость проходит основной маршрут:

1. Регистрируется, входит в систему
2. Выбирает дату, время, количество гостей — видит только допустимые окна
3. Создаёт бронирование (статус `pending`, стол назначается автоматически)
4. Открывает «Мои бронирования» и уведомления
5. Отменяет бронирование сам, если до начала больше 3 часов

Администратор (admin/super_admin) проходит второй маршрут:

1. Открывает административный контур
2. Фильтрует список бронирований по статусу и дате
3. Подтверждает / отменяет / завершает бронирование, отмечает no_show
4. Управляет столами и правилами доступности окон
5. (только super_admin) меняет роль пользователя user ↔ admin
6. Проверяет историю изменений (AuditLog)

## 1.2 Что не входит в текущую версию

- Внешние интеграции: платежи, email/SMS-провайдеры, OAuth/соцсети
- Публичный деплой и production-инфраструктура
- Мобильное приложение
- Мультитенантность (несколько ресторанов)
- Внешние уведомления — только внутренние, в интерфейсе

## 1.3 Допущения и открытые вопросы

### Допущения

- «Внутренние уведомления» — записи в БД, отображаемые в интерфейсе, без внешней рассылки
- Пересечение окон для стола проверяется по точному совпадению даты+времени слота (слоты дискретны, шаг 90 минут)
- Дедлайн отмены — 3 часа от текущего момента до `date`+`time` бронирования
- Деактивация стола не отменяет уже существующие бронирования, только исключает стол из будущего подбора

### Вопросы, которые нельзя восстановить из входа

- Нужна ли пагинация административного списка бронирований при большом объёме — для MVP допущение: без пагинации, с фильтрами
- Поведение при деактивации стола с активным бронированием — для MVP допущение: бронирование сохраняется как есть

## 2. Требования к результату

- Все сущности и правила из `specification.md` реализованы без расхождений
- Роль проверяется на сервере при каждом чувствительном действии, а не только в интерфейсе
- passwordHash никогда не покидает сервер в ответах API
- Правила доступности окон считаются динамически, не хранятся статичным списком
- Визуальная система Verde Marea (`design.md`) применена одинаково в гостевом и административном контуре
- Обязательные артефакты присутствуют: `specification.md`, `Plan.md`, `AGENTS.md`, `design.md`, `.env.example`, `README.md`/runbook, чек-лист приёмки, журнал проверок
- Ничего сверх зафиксированного в specification.md и этом плане не добавляется без обновления обоих документов

## 2.1 Раскладка по слоям

### Frontend
- Next.js App Router, React, TypeScript, Tailwind CSS, Zod
- Формы: регистрация, вход, бронирование (дата/время/гости)
- Личный кабинет гостя: список бронирований, уведомления, кнопка отмены
- Административный контур: список бронирований с фильтрами, управление столами, управление правилами окон, управление ролями (только super_admin), просмотр истории изменений
- Общие UI-токены и компоненты по `design.md` (кнопки, карточки, бейджи статусов, таблицы, формы, состояния loading/empty/error)

### Backend
- Next.js route handlers / server actions, TypeScript, Zod (те же схемы валидации, что и на клиенте)
- Сессии — упрощённый серверный механизм (без внешних auth-провайдеров)
- Проверка роли на сервере перед каждым чувствительным действием
- bcryptjs: `hash(password, 12)` при регистрации, `compare(inputPassword, user.passwordHash)` при входе
- Логика расчёта доступных окон, подбора стола, переходов статусов, проверки дублей — на сервере

### Database
- `User`: id, email, passwordHash, name, role, createdAt, updatedAt
- `Table`: id, name, capacity, isActive
- `Booking`: id, userId, tableId, date, time, guestsCount, status, createdAt, updatedAt
- `Notification`: id, userId, bookingId, message, isRead, createdAt
- `AuditLog`: id, actorId, action, targetType, targetId, metadata, createdAt

- роли (`User.role`): `user`, `admin`, `super_admin`
- статусы (`Booking.status`): `pending`, `confirmed`, `cancelled`, `completed`, `no_show`

- связи: `User 1—N Booking`, `User 1—N Notification`, `Table 1—N Booking`, `User 1—N AuditLog` (как actor)

- правило доступности окна: ближайшие 14 дней, вторник–воскресенье, шаг 90 минут, диапазон 12:00–21:00, без прошедшего времени, без занятых окон, только при наличии подходящего свободного стола
- правило подбора стола: минимально подходящая вместимость среди свободных на выбранное окно
- правило дублей: один пользователь — не больше одного активного (`pending`/`confirmed`) бронирования на дату+время; один стол — не больше одного бронирования на дату+время
- правило отмены: гость отменяет сам не позднее чем за 3 часа до `date`+`time`; после дедлайна — только admin/super_admin
- правило ролей: admin не может менять роль `super_admin` и не может назначать/снимать `admin`; только `super_admin` меняет `user` ↔ `admin`
