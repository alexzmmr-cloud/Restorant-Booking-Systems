# Spec — Verde Marea Booking System

## Назначение
- Гость ресторана Verde Marea быстро находит свободный стол на нужную дату, время и количество гостей и бронирует его без звонка администратору
- Гость видит свои бронирования и уведомления в одном месте, может сам отменить бронирование заранее
- Администратор видит весь поток заявок, управляет статусами, столами и окнами записи, не теряя историю действий
- super_admin управляет ролями пользователей отдельно от операционной работы admin

## Легенда
Verde Marea — ресторан с ограниченным залом и посадкой по столам разной вместимости. Бронирование велось вручную (звонки, блокнот), что приводило к двойным записям и потере истории. Система переводит запись на стол в управляемый цифровой процесс с прозрачными правилами доступности и единой историей изменений.

## Пользовательский сценарий
- Гость регистрируется и входит в систему
- Система открывает сессию
- Гость выбирает дату, время и количество гостей, видит только допустимые окна бронирования
- Гость создаёт бронирование — оно получает статус `pending`, система сама назначает подходящий свободный стол по вместимости
- Гость открывает раздел «Мои бронирования» и внутренние уведомления
- Гость отменяет своё бронирование самостоятельно, если до начала осталось больше 3 часов
- После дедлайна отмены гость не может отменить бронирование сам — только через администратора
- admin открывает административный контур, фильтрует бронирования по статусу и дате, меняет статусы
- admin управляет окнами записи (правилами доступности) и столами
- super_admin меняет роль пользователя (user ↔ admin) и проверяет, что история изменений зафиксировала ключевые действия
- Граничный случай: гость выбирает дату/время без доступных столов подходящей вместимости — система не предлагает такое окно в списке доступных

## Роли
- `user` — гость: бронирует, видит и отменяет свои бронирования, видит свои уведомления
- `admin` — управляет окнами записи, столами, бронированиями всех гостей (подтверждение/отмена/завершение/no_show); не может менять роль `super_admin` и не может назначать/снимать роль `admin`
- `super_admin` — все права `admin` + управление ролями: повышает `user` до `admin` и понижает обратно

## Сущность: User
- `id` — string (uuid)
- `email` — string, уникальный
- `passwordHash` — string (bcryptjs, 12 salt rounds), никогда не возвращается в API/UI
- `name` — string
- `role` — enum, см. «Разрешённые значения `role`»
- `createdAt` — datetime
- `updatedAt` — datetime

## Сущность: Table
- `id` — string (uuid)
- `name` — string (например «Стол 4»)
- `capacity` — number (вместимость, количество гостей)
- `isActive` — boolean (стол доступен для бронирования)

## Сущность: Slot (окно бронирования)
Окна не хранятся как статичный список — рассчитываются по правилам на лету (см. «Правила доступности окон»). Slot как расчётная единица описывается полями:
- `date` — date
- `time` — time (шаг 90 минут в диапазоне 12:00–21:00)
- `availableTables` — Table[] (столы, свободные на это окно, подходящие по вместимости)

## Сущность: Booking
- `id` — string (uuid)
- `userId` — string (ссылка на User)
- `tableId` — string (ссылка на Table, назначается системой при создании)
- `date` — date
- `time` — time
- `guestsCount` — number
- `status` — enum, см. «Разрешённые значения `status`»
- `createdAt` — datetime
- `updatedAt` — datetime

## Сущность: Notification
- `id` — string (uuid)
- `userId` — string (ссылка на User, получатель)
- `bookingId` — string (ссылка на Booking, опционально)
- `message` — string
- `isRead` — boolean
- `createdAt` — datetime

## Сущность: AuditLog
- `id` — string (uuid)
- `actorId` — string (ссылка на User, кто совершил действие)
- `action` — string (например `booking.confirmed`, `booking.cancelled`, `role.changed`)
- `targetType` — string (`Booking` | `User`)
- `targetId` — string
- `metadata` — json (детали изменения, например старый/новый статус или старая/новая роль)
- `createdAt` — datetime

## Разрешённые значения `role`
- `user`
- `admin`
- `super_admin`

## Разрешённые значения `status` (Booking)
- `pending` — создано, ждёт подтверждения
- `confirmed` — подтверждено администратором
- `cancelled` — отменено (гостем до дедлайна или администратором)
- `completed` — визит состоялся
- `no_show` — гость не пришёл

## Матрица ролей (кто может что)
- Создать бронирование — `user`
- Отменить своё бронирование до дедлайна (−3 часа) — `user`
- Просмотреть свои бронирования и уведомления — `user`
- Просмотреть список всех бронирований, фильтровать по статусу/дате — `admin`, `super_admin`
- Подтвердить (`pending` → `confirmed`) — `admin`, `super_admin`
- Отменить бронирование (любой статус, кроме терминальных) — `admin`, `super_admin`
- Завершить (`confirmed` → `completed`) — `admin`, `super_admin`
- Пометить неявку (`confirmed` → `no_show`) — `admin`, `super_admin`
- Управлять столами (создать/редактировать/деактивировать) — `admin`, `super_admin`
- Управлять правилами доступности окон — `admin`, `super_admin`
- Повысить `user` → `admin` — только `super_admin`
- Понизить `admin` → `user` — только `super_admin`
- Изменить роль `super_admin` — недоступно никому через интерфейс

## Машина состояний Booking
- `pending` → `confirmed` (admin/super_admin)
- `pending` → `cancelled` (user до дедлайна; admin/super_admin в любой момент)
- `confirmed` → `cancelled` (admin/super_admin; user — только до дедлайна)
- `confirmed` → `completed` (admin/super_admin)
- `confirmed` → `no_show` (admin/super_admin)
- Терминальные статусы (`cancelled`, `completed`, `no_show`) обратно в активные не переходят

## Требования к результату
- Доступные окна считаются по правилам: ближайшие 14 дней, со вторника по воскресенье, шаг 90 минут, диапазон 12:00–21:00, без прошедшего времени, без занятых окон, только при наличии подходящего по вместимости свободного стола
- Один пользователь не может иметь два активных (`pending`/`confirmed`) бронирования на одно и то же дату+время
- Один стол не может быть назначен двум бронированиям на пересекающееся окно (пересечение считается по факту совпадения даты+времени слота, так как слоты дискретны с шагом 90 минут)
- Подбор стола — по минимально подходящей вместимости среди свободных на выбранное окно
- passwordHash создаётся через `bcryptjs.hash(password, 12)`, проверяется через `bcryptjs.compare(inputPassword, user.passwordHash)`
- passwordHash никогда не входит в ответы API и не отображается в UI
- Все проверки прав и переходов статусов выполняются на сервере независимо от интерфейса
- Форму сущностей (поля выше) и списки разрешённых значений менять нельзя без обновления specification.md

## Данные
- Источник данных — PostgreSQL через Prisma
- Схема данных — `prisma/schema.prisma`, миграции — `prisma/migrations`
- Seed создаёт минимум: один `super_admin`, несколько столов разной вместимости, набор пользователей для проверки сценариев

## Frontend
- Next.js (App Router), React, TypeScript
- Tailwind CSS для стилизации по токенам из `design.md`
- Zod — валидация форм на клиенте (та же схема переиспользуется на сервере)

## Backend
- Next.js route handlers / server actions, TypeScript
- Zod — валидация входных данных на сервере
- Сессии — упрощённая серверная сессия (без внешних auth-провайдеров)
- Prisma Client — доступ к PostgreSQL

## Явно не входит в scope
- Внешние интеграции (платежи, email/SMS-провайдеры, соцсети, OAuth)
- Публичный деплой и production-инфраструктура
- Мобильное приложение
- Многоресторанность (мультитенантность)
- Уведомления во внешние каналы — только внутренние (в интерфейсе)

## Допущения
- «Внутренние уведомления» — записи в таблице Notification, отображаемые в интерфейсе гостя; email/SMS не рассылаются
- Пересечение окон для стола считается по точному совпадению даты+времени слота (не по произвольным интервалам), так как все бронирования привязаны к дискретным 90-минутным слотам
- Дедлайн отмены (3 часа) считается от текущего момента до `date`+`time` бронирования
- Единственный способ понизить `admin` до `user` — через `super_admin`; массовых операций над ролями не предусмотрено

## Открытые вопросы
- Что происходит с бронированием, если admin деактивирует стол, на который уже есть активное бронирование — требует уточнения (допущение по умолчанию: деактивация не влияет на уже созданные бронирования, только скрывает стол из будущего подбора)
- Нужна ли пагинация в административном списке бронирований при большом объёме данных — требует уточнения (для MVP допущение: полный список с фильтрами без пагинации)
